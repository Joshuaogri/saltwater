## 2. Verified behaviour

- Checkpoint capture uses one repeatable-read transaction and records explicit source environment/project/branch/database, schema watermark, canonical runtime state/tick, committed maximum event ID, event-work and schedule lifecycle counts, population count, optional business count, actor and approval references, and a stable manifest digest.
- Checkpoint restore validation reports separate gates. A failed or unexecuted gate is not hidden by an aggregate PASS.
- Recovery freezes dispatch by moving the runtime into RECOVERING with player absent. No wall-clock expiry or automatic claim reset is used.
- The owner domain must reconcile the effect against its authoritative records. A committed effect requires a durable outcome reference and is completed without handler re-execution. Confirmed absence releases the original event/idempotency identity to the failed/retry-eligible state. An indeterminate result is quarantined and blocks recovery completion.
- A quarantined item can be cleared only by a later conclusive owner response. Recovery decisions are idempotent, conflicting keys and stale claim tokens are rejected, and recovery/audit history is append-only.
- Recovery completion returns the runtime to READY with player absent. It does not advance the world tick.
- Causal prerequisites and BP35 event-attempt history remain intact.
